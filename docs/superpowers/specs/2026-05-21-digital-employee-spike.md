# 数字员工 Validation Spike 设计

**日期**：2026-05-21
**作者**：基于 `/plan-ceo-review` 决定（SCOPE REDUCTION + APPROACH A）
**适用项目**：test_agents
**预计周期**：7-14 天
**前置文档**：[`2026-05-21-digital-employee-design.md`](./2026-05-21-digital-employee-design.md)（待验证状态）

---

## 1. 为什么需要这个 Spike

原 `digital-employee-design.md` spec 经 CEO 审查后被判定为**预设性架构**：

- 🔴 **零真实任务数据**：test_agents 从未跑过真实代码变更分析或用例评审任务
- 🔴 **零业务方约束**：没有具体测试团队/产品线在等这个能力，3 个示例 tenant（订单/支付/会员）是模板
- 🔴 **零失败模式证据**：spec 设计的 8 大模块（评审员/规则/SOP/审批/黄金集/错题本/经验库/实验台）都基于"假设这些失败会发生"，但没有任何数据证明

> **核心问题**：在不知道"现在到底差在哪"的情况下建评估和进化系统，等于闭门造车——黄金集标什么？错题本记什么类型的错？规则兜底防什么？都是凭空想象。

**Spike 的唯一目的**：用 7-14 天产出**真实失败模式数据**，回答"是否真的需要建数字员工架构"。

---

## 2. Spike 范围

### 做什么

| # | 工作项 | 估时 | 产出 |
|---|---|---|---|
| 1 | 选取 5-10 个真实任务（覆盖不同类型） | 0.5-1 天 | 任务清单 + 已知风险点 |
| 2 | 用现有 test_agents 跑完所有任务 | 1-2 天 | 原始报告 N 份 |
| 3 | 资深测试人工标注每份报告失败模式 | 2-3 天 | 标注表（每份 1 个 markdown） |
| 4 | 聚类失败模式 → 分类报告 | 1-2 天 | 失败模式分类清单 |
| 5 | GO/NO-GO 决定 + 下一步推荐 | 1 天 | 决策文档 |

**总计**：5.5-9 天纯工作时间，含等待/沟通缓冲共 7-14 天。

### 不做什么

- ❌ 不写任何新代码（除非任务跑不起来需要修 bug）
- ❌ 不建评估系统（不要 Judge、不要黄金集、不要回归 CI）
- ❌ 不建治理设施（不要 SOP、不要审批、不要多租户）
- ❌ 不建进化系统（不要错题本、不要经验库、不要 prompt 实验）
- ❌ 不优化 prompt（先看现状，不要污染数据）

**纪律**：spike 期间任何"顺便优化一下"的冲动都是污染数据的行为，必须忍住。

## 3. 任务选取标准

### 3.1 数量与类型

选 **5-10 个真实任务**，必须覆盖以下类型（每类至少 1 个）：

| 类型 | 描述 | 目的 |
|---|---|---|
| **高风险变更** | 涉及支付/金额/状态机/数据迁移 | 测 Agent 对高风险信号的识别 |
| **逻辑复杂变更** | 多分支条件、复杂业务规则 | 测 Agent 的判断深度 |
| **简单 CRUD 变更** | 增删字段、改字段长度等 | 测基线，看简单场景是否也出错 |
| **跨模块影响** | 改 A 模块但隐式影响 B 模块 | 测 Agent 的影响面分析能力 |
| **"看似简单实际有坑"** | 表面 1 行改动，实际触发隐式契约 | 测 Agent 的"业务感" |

### 3.2 任务来源

**优先级 1（最佳）**：从公司**已合并的真实 PR** 中选——你（或团队）已经知道这些 PR 当时讨论/review 过什么风险

**优先级 2**：从公司**历史 bug 复盘**中反推——某个事故的修复 PR + 当时漏掉的风险

**优先级 3（兜底）**：开源项目的真实 PR + 你能查到 issue 讨论作为"标准答案"

### 3.3 任务输入格式

每个任务准备：

```yaml
# spike/tasks/task_001.yaml
id: task_001
type: high_risk_change       # 类型标签
description: "支付模块 refund 接口增加幂等性参数"

# 输入给 test_agents 的内容
input:
  user_request: "分析这个变更并评审相关测试用例"
  module: payment
  source_commit: a1b2c3d
  target_commit: e4f5a6b
  test_cases:
    - case_id: TC_REFUND_001
      title: "正常退款流程"
      steps: [...]

# 你/资深测试已知的"应该提到的风险点"（标注用）
known_risks:
  - id: r1
    desc: "幂等性参数缺失时的重复扣款风险"
    severity: HIGH
    why_known: "2025-08 真实事故 BUG-1234"
  - id: r2
    desc: "新参数对老客户端的兼容性"
    severity: MID
    why_known: "代码 review 时 @张三 提到过"
```

## 4. 标注方法

### 4.1 谁来标

- **必须由资深测试工程师标注**（5+ 年经验，做过此类业务的 review）
- 不能由 spec 作者或 LLM 标注（避免循环论证）
- 1 个标注人足够（多人标注会引入分歧，对 spike 阶段成本太高）

### 4.2 标注模板

每份 Agent 输出对应一份标注 markdown：

```markdown
# 任务 #N 标注 — <一句话任务描述>

## 任务输入
[复制 task yaml 的 input 段]

## Agent 输出原文
[完整粘贴 test_agents 跑出的报告]

## 标注

### 4.2.1 已知风险点命中情况
| 已知风险 ID | 命中？ | Agent 怎么说的（引用原文） |
|---|---|---|
| r1 | ❌ 漏 | （无） |
| r2 | ✅ 命中 | "建议测试老客户端是否能继续调用" |

### 4.2.2 失败项（逐一标注）

#### 失败 #1
- **类型**：漏风险 / 术语不准 / 证据虚 / 结论模糊 / 幻觉 / 其他
- **描述**：未提及 amount 字段 decimal→long 数据迁移风险
- **严重度**：HIGH / MID / LOW
- **人类本应怎么说**："金额字段类型变更必须验证历史数据兼容性，建议核对历史订单读取测试"
- **可修复假设**：
  - [ ] prompt 微调能修（如"在 system prompt 加一段'金额字段变更要查迁移'"）
  - [ ] 必须查知识库才知道（如"必须查 BUG-1234 才能想到这种风险"）
  - [ ] 必须有专门的规则兜底（如"硬规则：涉及金额字段必须提到迁移"）
  - [ ] 模型能力问题（如"换更强模型可能就修了"）

#### 失败 #2
...

### 4.2.3 总体评分（主观 1-5）
- **风险覆盖**：2/5 — 漏了 r1（HIGH），命中 r2（MID）
- **业务感**：3/5 — 用对了"幂等性"但没用公司内部术语
- **证据强度**：2/5 — 论断未引用具体 commit / bug
- **可执行性**：3/5 — 建议比较泛，缺具体测试步骤

### 4.2.4 一句话定性
"这份报告水平相当于一个刚来 3 个月的初级测试——能看到表面，但漏了历史教训。"

### 4.2.5 如果让我从零修，最快路径
"加 2 个东西就好：(1) prompt 里塞一段'金额字段类型变更必查迁移'；(2) 让 Agent 能查 BUG 库。
**不需要建 Judge、不需要建 SOP**——加这两个我估计能修 80%。"
```

### 4.3 标注时禁忌

- **不要修改 Agent 输出**（哪怕只是格式）
- **不要标"如果 Agent 多想一步就好了"**——只标具体差异
- **必须填"可修复假设"那一项**——这是 GO/NO-GO 判定的最关键输入
- **每个失败必须给出"人类本应怎么说"的具体话术**——含糊的标注=没有标注

## 5. 聚类与分类报告

5-10 份标注完成后，做一份**失败模式聚类报告**：

```markdown
# Spike 失败模式分类报告

## 总览
- 任务数：N
- 失败总数：M
- 平均每份报告失败数：M/N

## 失败模式聚类（按出现频次降序）

### 聚类 1：漏隐式业务规则（出现 X 次，占比 X%）
- 典型例子：
  - task_001 漏 amount 迁移
  - task_003 漏 status_history 同步
  - task_007 漏 refund 幂等
- **修复假设分布**：
  - prompt 微调可修：1 个
  - 必须查知识库：3 个
  - 必须规则兜底：1 个
- **结论**：**需要知识工具化 + 部分硬规则**，prompt 改不动

### 聚类 2：业务术语不准（出现 X 次）
- 典型例子：...
- **修复假设分布**：
  - prompt 微调可修：4 个（在 prompt 加术语表）
- **结论**：**纯 prompt 工程问题**，不需要任何架构变更

### 聚类 3：...

## 严重度 × 修复成本矩阵

|              | prompt 可修 | 需查知识 | 需规则兜底 | 模型能力 |
|--------------|-------------|----------|------------|----------|
| HIGH 失败    | A 个        | B 个     | C 个       | D 个     |
| MID 失败     | ...         | ...      | ...        | ...      |
| LOW 失败     | ...         | ...      | ...        | ...      |

## 关键发现
- [写 3-5 条最重要的观察]
```

## 6. GO / NO-GO 判定

### 6.1 GO 条件（值得建数字员工架构）

**同时满足**：
1. ✅ 失败模式中 **≥ 3 类是 prompt 微调解决不了的**
2. ✅ 失败模式间有**系统性规律**（不只是"这个模型不行"）
3. ✅ 5-10 个任务中 **≤ 30% 是"prompt 微调就能修好"**

### 6.2 NO-GO 条件（不需要建架构）

**满足任一**：
1. ❌ 大部分失败都是"prompt 没写清楚"或"缺一个 checklist 段"
2. ❌ Agent 的主要问题是"输出格式/风格"而非"判断力/业务感"
3. ❌ 5-10 个任务中有 ≥ 50% 是"prompt 调一下就能修好"

### 6.3 PARTIAL 条件（只建一部分）

如果既不全 GO 也不全 NO-GO：
- 根据失败模式聚类，**只挑前 1-2 类对应的原 spec 模块先做**
- 其他模块全部延后或丢弃

## 7. 决策文档模板

Spike 结束后产出最终决策文档：

```markdown
# Spike 决策报告

## 结论：GO / NO-GO / PARTIAL

## 关键数据
- 任务数：N
- 标注失败总数：M
- prompt 可修占比：X%
- 需架构干预占比：Y%

## 如果 GO 或 PARTIAL：推荐先做的模块

按"原 spec 模块 ↔ 解决哪类失败"的映射：

| 失败聚类 | 推荐先做的原 spec 模块 | 不做的模块 |
|---|---|---|
| 漏隐式业务规则 | B2 知识工具集 + R3 主动查询 | Judge/规则/SOP/错题本 |
| 判断力差 | A2 评审员（最小版） + L4 升级 | 规则/SOP/经验库 |
| 质量不稳定 | C1 黄金集 + Judge 4 维评分 | SOP/审批/反馈/经验库 |

**第一阶段实施范围**：[基于上表挑出 1-2 个模块]
**第一阶段时间估算**：[基于实际范围重新估算]

## 如果 NO-GO：推荐改进方向

- 调整哪几个 prompt：[列出]
- 是否加一个简单的 RAG 检索工具：是/否
- 原 spec 的处置：标记为 deprecated

## 重写 spec 计划

[基于结论，决定是修订原 spec 还是新写一份精简版]
```

## 8. Spike 风险与守住的事

| 风险 | 守住的事 |
|---|---|
| 标注人主观偏差 | 同一份报告，要求标注人填"可修复假设"的具体路径，迫使思考可解决性，不只是"我不满意" |
| 任务选样偏差（太难或太简单） | 必须覆盖 3.1 中所有类型；事先记录"已知风险点"作为客观基准 |
| 标注变成"挑刺比赛" | 评分卡 4 维度（覆盖/术语/证据/可执行性）锚定标注口径 |
| Spike 期间手痒去优化 prompt | 纪律性约束：spike 期间任何代码变更都需要在日志中标注"为何不能等到 spike 后" |
| 7-14 天拖到 4 周 | 每天产出阶段性进度文档，第 7 天必须有"至少跑完一半任务"的硬节点 |
| GO/NO-GO 判定模糊 | 第 6 节判定条件用硬数字（30%、50%）而非主观，避免"感觉不太行/感觉还行" |

## 9. Spike 与原 spec 的关系

| 维度 | 原 spec | Spike |
|---|---|---|
| 状态 | pending validation | active |
| 范围 | 8 模块 × 4 阶段 × 多租户 | 跑任务 + 标注 + 决策 |
| 工时 | 16-20 周（4 阶段） | 7-14 天 |
| 编码量 | 大量新模块 | 几乎为零 |
| 回答的问题 | "怎么建数字员工" | "要不要建数字员工 + 该建哪部分" |
| 完成后 | 进入实施 | 改写原 spec 或废弃原 spec |

## 10. Spike 不做什么（YAGNI 清单）

明确**不在本 spike 范围**：
- ❌ 任何评估系统（Judge、黄金集、规则引擎、回归 CI）
- ❌ 任何治理设施（SOP、审批队列、多租户、岗位说明书、审计日志、运营监控）
- ❌ 任何进化系统（错题本、反馈通道、经验库、prompt 实验台）
- ❌ 任何知识抽取（D1 Git/D2 PR/D3 Bug pipeline 全部不做）
- ❌ 任何工具新增（不加 query_similar_bugs 等工具）
- ❌ 任何 prompt 优化（保持现状以收集真实数据）
- ❌ 任何性能/可观测改造
- ❌ 任何 UI 改造

**如果 spike 期间发现现有 test_agents 跑不起来真实任务（如 bug、配置缺失），仅修复阻塞性问题，
不做任何"顺便改进"**——所有改动需在 spike 日志中说明"为什么不能等到 spike 后再做"。

## 11. 下一步

Spike 结束后产出"Spike 决策报告"，根据结论：

- **GO**：基于失败聚类，**重写一份精简版 spec**（不是激活原 spec 全部），只挑前 1-2 个真正能解决已观测失败的模块。新 spec 走完整的 `/brainstorming` → `/plan-ceo-review` → `/plan-eng-review` → `writing-plans` 流程
- **NO-GO**：原 spec 标记为 `status: deprecated — validated unnecessary by spike`。建立一份简短的"prompt 工程改进清单"
- **PARTIAL**：与 GO 处理相同，但精简版 spec 范围更小
